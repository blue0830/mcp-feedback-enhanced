## MCP→CLI 改造评估（explore 结论，未实施）

- **可行性：改动小**。核心入口 `launch_web_feedback_ui(project_dir, summary, timeout) -> dict`（web/main.py:1099）协议无关，MCP 只是包装层；web/main.py `__main__` 测试已验证直接调用路径可行。
- **最小改动清单**：新增 `cli.py`（argparse + init_encoding + 调 launch_web_feedback_ui + `create_feedback_text` 复用 + 图片落盘打印路径）~100 行；`pyproject.toml` [project.scripts] 加 1 行。server.py / web 层零改动，MCP 与 CLI 并存。
- **多实例**：CLI 每调用一进程 = 天然多实例（MCP stdio 其实也已是每客户端一进程）。注意点：a) `_check_active_tabs` 只查进程内存 → CLI 无法复用浏览器标签页，每次弹新窗（多 Agent 场景下正好每 Agent 一窗）；b) `session_history.json`/`ui_settings.json` 多实例互相覆盖（agent-cli-control.md O5 已定为不正交不解决，CLI 场景 stdout 返回主流程不受影响）。
- **响应速度真相**：一次性 CLI 每次付冷启动（import + `start_server` 硬编码 `time.sleep(2)` + uvicorn）≈3-5s；MCP 常驻进程仅首次慢。CLI 的真实收益是**摆脱 MCP 客户端 per-request 超时掐断**（见 MEMORY.md 架构关键事实第 2 条），走 Bash 工具超时可配。要极致快需 daemon 模式（复用 agent-cli-control.md 的 instance_registry 设计，该 change 未实施）。
- 用户目的确认：加快响应 + 多实例，评估结论 = 直接 CLI 化改动很小，daemon 模式是可选增强非必须。
- 追问结论：a) 多实例严格 1:1（三层隔离：端口 WebSocket 路由 / 进程内 Event / OS stdout 管道），唯一风险是人为看错窗口；b) 阻塞语义保持（进程不退出 = Bash 不返回），注意外层 Bash 超时须 > 内层 --timeout（WorkBuddy Bash max 600s → timeout ≤590）；c) 核心功能不变，差异仅图片落盘 Read、跨调用连续性略降。
